# Reproducing the pinned specification

`spec/openapi.raw.json` is the OpenAPI document this library is built from. Whisparr 2 serves no
spec endpoint, so the document is not captured from a running instance. It is a git blob in
`Whisparr/Whisparr`, addressed by commit.

This document is how you reproduce that file from a fresh clone and get the committed bytes back.
You do not need to be the author of this repository to do it. One command re-verifies the pin
against the upstream repository, and three commands verify the committed file with no network at
all.

## Provenance

Four scripts write `spec/PROVENANCE.json`. `generator/fetch_spec.py` writes the spec block after
it has verified the bytes it fetched. `generator/verify_image.py` writes the image block after it
has booted the pinned digest and read the identity the instance reported.
`generator/preprocess_spec.py` writes `generatedSpecSha256` after it has written the patched
specification. `generator/generate.py` writes `generatedTreeSha256` after it has replaced the
generated client tree. The four acquisitions are independent, so the table names the writer of
every field: a reader who finds one block wrong knows which script to re-run.

A fetch drops `generatedSpecSha256` and pre-processing puts it back. A new capture invalidates the
patched specification, so the field is removed rather than left describing a document that no longer
follows from the pin.

`specRefName` is recorded and never used. The fetch URL carries the commit and never a ref name,
because a ref name moves and the whole point of the pin is that it does not.

`generatedSpecSha256` is the one row that can move while the pin stands still. It is the hash of a
file this repository produces, so it changes whenever `generator/preprocess_spec.py` changes what
the patching does. A changed value in a diff is not by itself evidence of a moved pin.

`generatedTreeSha256` is one hash over the whole generated client tree: the 221 source files under
`src/Whisparr2.Net/`, the two files under `.openapi-generator/` and `.openapi-generator-ignore`,
224 files in total. It is computed over the sorted list of relative paths and the file bytes
together, so a rename, an addition, a deletion and an edit each move it. It covers exactly the
files `generator/generate.py` deletes and rewrites, which is why the hand-owned
`src/Whisparr2.Net/Whisparr2.Net.csproj` and the build output beside it are outside it.

Two mechanisms read it. `generator/generate.py` checks the committed tree against this value
before it deletes anything, and refuses when they disagree. `generator/selftest.py` checks the
same thing offline, which is what catches an edit that was committed and so no longer shows in
`git status`.

`spec/PROVENANCE.json` is the authoritative copy of all of it, along with the wall clock of the
fetch and the URL it was fetched from. The table above restates it so a reader does not have to open
the file, and the file wins if the two ever disagree. The file is generated by the four scripts
and is never hand-edited.

## Prerequisites

- Python 3. The generator scripts import only the standard library, so there is nothing to install
  alongside it.
- A reachable Docker daemon, needed by `generator/verify_image.py`, by `generator/generate.py` and
  by `generator/selftest.py --docker`. The fetch does not use it, and neither does the offline
  verification.

Commands below are given in two interpreter forms. On Linux and macOS use `python3`. On Windows use
`python`. The difference is not cosmetic: `python3` is the name that resolves on a typical Linux or
macOS installation, and it does not resolve on every Windows installation, where `python` does.

## Re-verify the pinned specification

One command, from the repository root. It takes no arguments.

```
python3 generator/fetch_spec.py
```

```
python generator/fetch_spec.py
```

What it does, in order. It builds the raw URL from the pinned commit. It fetches the document. It
checks the byte count, then the sha256, then the git blob identity, all three against values held as
constants in the script. It checks that the document declares `/api/v3/series` and `/api/v3/episode`
and does not declare `/api/v3/movie` or `/api/v3/alttitle`, which is the only thing separating this
document from the Whisparr 3 one in the same repository. It checks that the document declares a
3.0.x OpenAPI version and carries the malformed root path. Only then does it write.

A re-verify changes nothing except the `fetchedAt` line in `spec/PROVENANCE.json`. That is the
correct outcome, not a missing step. The spec file itself is rewritten with identical bytes, so
`git status` reports it unchanged.

## Move the pin

Follow the steps in order. None of them is optional.

The steps substitute three placeholders:

- `<sha40>` is the candidate commit, written as 40 lowercase hex characters. An uppercase spelling
  of the same commit, a value carrying surrounding whitespace, and a ref name such as `v2` are each
  refused at the commit-taking flags. The refusal table below quotes the message.
- `<hex64>` is the sha256 of the candidate's bytes, read from the output of step 1.
- `<n>` is the byte count of the candidate, read from the output of step 1.

1. Propose the candidate commit. This mode fetches read-only, prints the observed size, sha256 and
   blob sha1, and writes nothing.

   ```
   python3 generator/fetch_spec.py --propose <sha40>
   ```

   It runs the Whisparr 2 check and the OpenAPI check on the candidate, so a proposal against the
   wrong application refuses in words rather than printing values that invite a paste.

2. Write the move, stating all three values in advance.

   ```
   python3 generator/fetch_spec.py --commit <sha40> --expect-sha256 <hex64> --expect-bytes <n>
   ```

   The three flags are accepted only together. Supplying some of them is a refusal, not a bypass,
   and there is no force flag. A caller who supplies `--commit` alone sees this:

   ```
   fetch_spec.py: error: moving the pin requires --commit, --expect-sha256 and --expect-bytes together; missing --expect-sha256, --expect-bytes. Run --propose <sha40> to observe the values first.
   ```

3. Update `SPEC_COMMIT`, `EXPECTED_BYTES` and `EXPECTED_SHA256` in `generator/fetch_spec.py` to the
   accepted values, in the same commit that moves the spec. `EXPECTED_BLOB_SHA1` moves with them.
   The script prints the four lines to copy at the end of a successful move.

   A skipped step 3 costs the move. The next plain `python generator/fetch_spec.py` refetches the
   old commit, passes its checks against the old constants, and rewrites both the spec and the
   provenance back to the old pin. The move prints a warning naming each stale constant, so the
   omission is visible at the time, but nothing later catches it.

4. Re-run the image check, because a spec move usually accompanies a release move. See the section
   below.

## Re-verify offline, with no network

Three commands on a clone. None reaches the network and none needs Python.

```
git hash-object spec/openapi.raw.json
sha256sum spec/openapi.raw.json
wc -c spec/openapi.raw.json
```

Each must produce the value recorded in `spec/PROVENANCE.json`:

| Command | Must print | Recorded as |
| --- | --- | --- |
| `git hash-object spec/openapi.raw.json` | `a3037cf379826505dc4557e74bf0798f43f2d4b8` | `specBlobSha1` |
| `sha256sum spec/openapi.raw.json` | `e16d5052c6da3fdb9c54739890412c340c4b485c0a1b53af15f5a6ac837bb0a2` | `specSha256` |
| `wc -c spec/openapi.raw.json` | `282862` | `specBytes` |

`git hash-object` prints git's own object identity for the file. That is the same value the upstream
commit records for that path, and the same value `generator/fetch_spec.py` asserts before it writes.
Together the three say that the committed file is the exact blob commit `face3be8` records at
`src/Whisparr.Api.V3/openapi.json`.

`git hash-object` needs no repository. It runs in any directory, so a reader can check a downloaded
copy without cloning.

On Windows without Git Bash, `certutil -hashfile spec\openapi.raw.json SHA256` is the sha256 command
and produces the same value.

If `git hash-object` agrees and `sha256sum` disagrees, the working copy was converted to CRLF on
checkout. Check that `.gitattributes` still carries the `spec/openapi.raw.json -text` line.

## Pre-process the specification

One command, from the repository root. It takes no arguments.

```
python3 generator/preprocess_spec.py
```

```
python generator/preprocess_spec.py
```

It reads `spec/openapi.raw.json` and writes `spec/openapi.generated.json`, the document the
generator is run against. It then writes the sha256 of that file into `spec/PROVENANCE.json` as
`generatedSpecSha256`. Both outputs are committed.

The patched document is committed rather than built into an ignored path because the diff between
the two spec files is the review artifact of a spec refresh. It shows a reviewer what pre-processing
did to the new pin. A hash recorded over a file no reviewer can open records nothing.

What it does, in order. It narrows root security to the header scheme, so the generated client does
not send the key in the URL of every request. It deletes the malformed root path, which declares a
required path parameter that the path template carries no placeholder for. It derives an operation
identifier for every operation from the document itself and assigns it, refusing on a name carried
by two operations and on a name that is not a valid identifier. It rewrites the five schemas shaped
like framework types to strings and deletes the five. Then it counts the operations it annotated
against the operations it parsed less the ones the root-path delete removed. Only then does it
write.

A clean run over the current pin reports change counts of 1, 1, 227 and 10, then a census of 228
operations in, 1 removed by the root-path delete and 227 out. The patched document carries 156 path
items and 129 schemas.

The two spec files differ by one cosmetic line as well as by the four transformations. Python spells
an empty collection `{}` where the .NET writer that produced the pinned document spells it `{ }`,
and the patched file ends with a newline where the pinned one does not. Two more such sites sit
inside the root security value, which the first transformation rewrites anyway.

Each transformation refuses when it finds nothing to change. An upstream fix therefore fails this
step rather than leaving a rewrite in the pipeline that no longer does anything. The repair is to
delete the transformation, not to weaken it until it passes.

The script is not re-runnable over its own output. Pointing `--raw-spec` at
`spec/openapi.generated.json` makes all four transformations refuse at once. That is the correct
result and not a defect.

Run it when the pin moves, before generation. Not per change.

`spec/openapi.generated.json` is generated by the script and is never hand-edited.

## Generate the client

One command, from the repository root. It takes no arguments. It requires Docker.

```
python3 generator/generate.py
```

```
python generator/generate.py
```

It runs the pinned generator image
`openapitools/openapi-generator-cli@sha256:2ab0a9680222de65dc9d3baf861aa02b99e1b80c211d8221ebf3ae8f8a102524`,
which is openapi-generator-cli 7.25.0. The digest is held as `DEFAULT_IMAGE_DIGEST` in
`generator/generate.py` and restated in the header of `generator/gen-config.yaml`. The digest is the
pin and the tag is not, because a tag can be moved onto other bytes.

Generation never bind-mounts this repository. It copies `spec/openapi.generated.json` and
`generator/gen-config.yaml` into a fresh temporary root, mounts that, and stages nothing else. There
are two reasons. The generator writes into the root it is given and never prunes, so a run against
the repository in place would mix its output into the working tree before any check had seen it. And
a repository on a mapped or network drive may not be bind-mountable at all: a bind mount of a
mapped-drive path into this image lists as an empty directory and exits 0, while a write into that
mount succeeds inside the container and never reaches the host. That is silent data loss rather than
an error, and it is why there is no output-root parameter.

If you reproduce the `docker run` by hand in Git Bash, prefix it with `MSYS_NO_PATHCONV=1`. Without
it MSYS rewrites `/local` into a Windows path and the mount target is wrong. Python's `subprocess`
does not go through MSYS, so the script itself is unaffected.

The staged tree is gated before anything committed is deleted. In order:

1. The five generated subdirectories `Api`, `Client`, `Extensions`, `Logging` and `Model` all exist.
2. The three metadata files `.openapi-generator/FILES`, `.openapi-generator/VERSION` and
   `.openapi-generator-ignore` all exist.
3. Every `Model/` and `Api/` file name the spec implies was generated, and no name it does not imply.
4. Every method name the spec declares is implemented.
5. `Client/`, `Extensions/` and `Logging/` each hold at least one `.cs` file.
6. The committed tree still matches `generatedTreeSha256`.

Every one of the six runs before the first delete. Step 6 is the pre-flight: it runs after the gate
has approved the staged tree and immediately before the first unlink.

Step 6 refuses on three states, not one. A committed tree whose bytes no longer match the recorded
digest is a hand edit. A committed tree missing one of the five subdirectories is a tree already
damaged, and it refuses rather than treating the absence as a first run. Only a tree with no
recorded digest and none of the five subdirectories is a first run, and that establishes the
digest.

A clean run over the current pin stages 221 `.cs` files, reports that all 227 method names the spec
declares are implemented, copies 221 `.cs` files back, and prints the digest it wrote.

It writes the five subdirectories under `src/Whisparr2.Net/`, `.openapi-generator/`,
`.openapi-generator-ignore` and the one provenance field `generatedTreeSha256`. All of it is
committed, for the same reason the patched specification is: the diff is the review artifact of a
refresh.

```
python3 generator/generate.py --check
```

```
python generator/generate.py --check
```

`--check` runs the identical generation and the identical gate, compares the result against the
committed tree and writes nothing anywhere. A clean check reports that all 224 files match byte for
byte. It exits 0 when the committed tree is byte-identical to a fresh generation, 1 when it differs
or the gate refused, and the generator's own exit code when the image itself failed.

Nothing under `src/Whisparr2.Net/` except `Whisparr2.Net.csproj` is ever hand-edited. The csproj is
hand-owned and sits beside the five generated subdirectories, which is why the delete iterates the
five and never the package root. When the method census refuses because the generator renamed an
operation, the repair is an override entry in `generator/preprocess_spec.py`, never an edit under
the generated tree. A hand edit there is discarded by the next run, and refused by the pre-flight
before that.

On Windows a regeneration can fail partway through the copy with a sharing violation, because
MSBuild node processes hold build directories open. Run `dotnet build-server shutdown` first, then
re-run the generator.

Run it when the pin moves, after pre-processing. Not per change.

## Verify the container image

One command. It requires Docker.

```
python3 generator/verify_image.py
```

It boots the pinned digest with a seeded `config.xml`, reads the system status endpoint with the
seeded key, and refuses unless the instance reports branch `v2` and major version 2. The same image
name carries tags for Whisparr 3, and the application name and the API prefix are identical on both,
so neither of those discriminates.

Only then does it merge the six image fields into `spec/PROVENANCE.json`. The container is removed
whether the run succeeded or failed, so nothing is left holding a published port and a live key.

Run it when the pin moves, not per change.

## Refresh the whole pipeline

Four commands, in this order. Each one writes a committed artifact.

```
1. python generator/fetch_spec.py
2. python generator/verify_image.py
3. python generator/preprocess_spec.py
4. python generator/generate.py
```

Step 3 must precede step 4. `generator/generate.py` stages `spec/openapi.generated.json`, which is
step 3's output, so running step 4 first regenerates the client from the previous pin and reports
nothing wrong.

Step 2 is independent of the other three and can run at any point after the pin moves. It is placed
second because a spec move usually accompanies a release move, and running it before generation
means the recorded image identity and the recorded tree describe the same refresh.

Follow the four with `dotnet build Whisparr2.Net.slnx`, which must report 0 errors and 0 warnings on
both target frameworks.

There is no single command that runs all four. Each writes a committed artifact and each has its own
refusals, and a wrapper that hides which of them refused is worse than four lines a reader can run
one at a time.

## What the scripts refuse, and why

Every refusal exits non-zero and leaves the tree untouched. Find yours by its first line.

| First line | Cause |
| --- | --- |
| `ERROR: REFUSED - this document declares /api/v3/movie, /api/v3/alttitle and not /api/v3/series, /api/v3/episode.` | The fetched document is the Whisparr 3 one from the same upstream repository. |
| `fetch_spec.py: error: moving the pin requires --commit, --expect-sha256 and --expect-bytes together;` | A move was attempted without stating all three expected values. |
| `fetch_spec.py: error: --propose writes nothing and cannot be combined with --commit.` | A read-only proposal was combined with a move flag. |
| `fetch_spec.py: error: argument --commit: 'v2' is not a 40-character lowercase hex commit SHA.` | The value is not 40 lowercase hex characters: a ref name such as `v2`, an uppercase spelling of a real commit, a value carrying surrounding whitespace, or a value of any other length. | `ERROR: REFUSED - the body is 337327 bytes, expected exactly 282862.` | The fetched byte count disagrees with the pin. |
| `ERROR: REFUSED - sha256 is <observed>, expected <expected>.` | The fetched bytes hash to something other than the pin. The blob sha1 has its own line in the same form. |

## Checking the scripts themselves

`python generator/selftest.py` runs 26 offline assertions over the fetch, the pin,
pre-processing, the image identity and the generation gate, and needs no network and no Docker.
`python generator/selftest.py --network` adds the assertions that fetch real commits from
`raw.githubusercontent.com`, for 27. `python generator/selftest.py --docker` adds the full
regeneration, also for 27; it needs the pinned image and takes about a minute.
`python generator/selftest.py --network --docker` runs all 28. Every one of them is run by hand
today.
