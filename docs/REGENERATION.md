# Reproducing the pinned specification

`spec/openapi.raw.json` is the OpenAPI document this library is built from. Whisparr 2 serves no
spec endpoint, and the document committed upstream at `src/Whisparr.Api.V3/openapi.json` is
regenerated by hand and has three commits in its whole history, so it omits fields the running
application returns at the same commit. This repository therefore builds Whisparr 2 from source at
a pinned commit and captures the document its own controllers produce.

This document is how you reproduce that file from a fresh clone and get the committed bytes back.
You do not need to be the author of this repository to do it. One command builds and captures, and
two commands verify the committed file with no network at all.

## Provenance

Three scripts write `spec/PROVENANCE.json`. `generator/build_spec.py` writes the spec block after
it has built the application and accepted the document it captured. `generator/preprocess_spec.py`
writes `generatedSpecSha256` after it has written the patched specification.
`generator/generate.py` writes `generatedTreeSha256` after it has replaced the generated client
tree. The three writes are independent, so the table names the writer of every field: a reader who
finds one block wrong knows which script to re-run.

Two fields have no script that runs to produce them. `imageTag` and `imageDigest` are constants in
`generator/container.py`, which is the single place the pinned Whisparr image is named. They reach
the provenance record through the offline self-test, which asserts that the recorded digest and the
module's constant are the same image.

`spec/CONFORMANCE.json` is not part of `spec/PROVENANCE.json`, and no script writes a provenance
field for it. It records `imageDigest` as the image reference the sweep passed to Docker, and
`specCommit` from the provenance record, so a reader can tell whether the record was measured
against the pin that is committed now. The digest is the run's own rather than a copy of the
provenance field, because copying it would leave the fifth transformation comparing one field
against itself. The sweep refuses before it boots when the two disagree. It records no hash of the
patched document, because the fifth pre-processing transformation rewrites that document from this
very record: any hash recorded would be the hash of the document as it stood before the record was
applied to it. It has no `.gitattributes` line: nothing records its hash, and the point of the file
is that a reviewer reads its diff.

A build drops `generatedSpecSha256` and pre-processing puts it back. A new capture invalidates the
patched specification, so the field is removed rather than left describing a document that no longer
follows from the pin.

The three count fields are recorded and are not restated here. They are measured from the captured
document on every build, and `spec/PROVENANCE.json` is where their current values are read.

`specRefName` is recorded and never used. The build fetches the commit and never a ref name,
because a ref name moves and the whole point of the pin is that it does not.

`sdkImageDigest` and `swashbuckleCliVersion` are recorded because they are inputs to the bytes. The
document is an output of a build, so the SDK the build ran in and the version of the capture tool
are part of what determines it, in the same way the source commit is.

`generatedSpecSha256` is the one row that can move while both pins stand still. It is the hash of a
file this repository produces, so it changes whenever `generator/preprocess_spec.py` changes what
the patching does, and it changes when the conformance record the fifth transformation reads is
re-measured. A changed value in a diff is not by itself evidence of a moved pin.

`generatedTreeSha256` is one hash over the whole generated client tree: the source files under
`src/Whisparr2.Net/`, the two files under `.openapi-generator/` and `.openapi-generator-ignore`. It
is computed over the sorted list of relative paths and the file bytes together, so a rename, an
addition, a deletion and an edit each move it. It covers exactly the files `generator/generate.py`
deletes and rewrites, which is why the hand-owned `src/Whisparr2.Net/Whisparr2.Net.csproj` and the
build output beside it are outside it.

Two mechanisms read it. `generator/generate.py` checks the committed tree against this value before
it deletes anything, and refuses when they disagree. `generator/selftest.py` checks the same thing
offline, which is what catches an edit that was committed and so no longer shows in `git status`.

`spec/PROVENANCE.json` is the authoritative copy of all of it. The table above restates the pins and
the hashes so a reader does not have to open the file, and the file wins if the two ever disagree.
The file is generated by the three scripts and is never hand-edited.

## Prerequisites

- Python 3. The generator scripts import only the standard library, so there is nothing to install
  alongside it.
- A reachable Docker daemon, needed by `generator/build_spec.py`, by `generator/generate.py`, by
  `generator/conformance.py` and by `generator/selftest.py --docker`. The offline verification and
  the offline self-test need neither Docker nor a network.
- An outbound network route, needed by `generator/build_spec.py` and by the one sweep read behind
  `WHISPARR2NET_CONFORMANCE_EXTERNAL`. The build pulls the .NET SDK image from `mcr.microsoft.com`,
  fetches the pinned commit from `github.com` and installs the capture tool from nuget.org. None of
  the three is vendored here. The flagged sweep read reaches a metadata service over the public
  internet.

Commands below are given in two interpreter forms. On Linux and macOS use `python3`. On Windows use
`python`. The difference is not cosmetic: `python3` is the name that resolves on a typical Linux or
macOS installation, and it does not resolve on every Windows installation, where `python` does.

## Build the specification and capture it

One command, from the repository root. It takes no arguments.

```
python3 generator/build_spec.py
```

```
python generator/build_spec.py
```

It needs Docker and it needs outbound network, and it takes several minutes. It pulls the pinned
.NET SDK image, initialises an empty checkout inside a container, fetches the pinned commit by SHA,
builds `src/Whisparr.sln` for `linux-x64`, installs the pinned Swashbuckle CLI into that container
and runs it against the built assembly.

The capture runs twice from the one build, into two files, and the two are compared byte for byte
before either is accepted. A difference would mean the document embeds a timestamp, a path or a
hash-ordering artifact, which is silent and expensive to unwind once a client tree is committed on
top of it. Both captures come from one built assembly, so nothing else could explain it.

Being killed is the expected end of a successful capture. The Swashbuckle CLI boots the full
application host, migrates a database and never exits after writing the file, so the capture runs
under a kill timeout and exit 137 is accepted while every other non-zero status is not.

Only then does the script check the document. It must declare a 3.0.x OpenAPI version, it must
declare `/api/v3/series` and `/api/v3/episode`, and it must not declare `/api/v3/movie` or
`/api/v3/alttitle`. That path check is the only thing separating this document from the Whisparr 3
one built from the `eros` branch of the same repository: both declare the same `openapi` version,
the same `info.version` and the same `info.title`. Only after all of it does the script write.

A re-run changes nothing except the `builtAt` line in `spec/PROVENANCE.json`. That is the correct
outcome, not a missing step. The spec file itself is rewritten with identical bytes, so `git status`
reports it unchanged.

Run it when a pin moves. Not per change.

## Move the pin

Change `SPEC_COMMIT` in `generator/build_spec.py` to the candidate commit and re-run the script.
There is no proposal mode and no set of expected-value flags, because nothing is being fetched and
compared against a recorded identity: the bytes are produced here, and the values that describe them
are measured from what the build produced.

What makes the move fail closed is the pair of checks above. A commit on the wrong branch builds the
wrong application, and the path check refuses the document it produces. A build that is not
reproducible fails the two-capture comparison. Both write nothing, and there is no force flag.

Two pins move together in practice, and they are pinned separately on purpose. `SPEC_COMMIT` in
`generator/build_spec.py` is the source the client is generated from, and `IMAGE_DIGEST` in
`generator/container.py` is the application every live measurement runs against. A release move
usually moves both. Neither is a floating tag: the `:v2` tag moves, and so does the
release-numbered `v2-2.2.0-release.231` tag, which was re-pushed while the pinned digest stayed
resolvable.

After a spec move, re-run the pipeline in the order the refresh section gives. The conformance sweep
is not optional there: the fifth pre-processing transformation reads what the sweep records.

## Re-verify the committed document offline

Two commands on a clone. Neither reaches the network and neither needs Python.

```
sha256sum spec/openapi.raw.json
wc -c spec/openapi.raw.json
```

Each must produce the value recorded in `spec/PROVENANCE.json`:

| Command | Must print | Recorded as |
| --- | --- | --- |
| `sha256sum spec/openapi.raw.json` | `b1c0783ad977354249bac5eda930a4681789a1e02c9552dae63f1b6202816f93` | `specSha256` |
| `wc -c spec/openapi.raw.json` | `291311` | `specBytes` |

Together the two say that the committed file is the exact document the recorded build produced. They
say nothing about where it came from, and they cannot: the document is built here rather than read
out of another repository, so it has no stored object identity anywhere else to compare against.
The source it was built from is identified by `specCommit`, and reproducing it means re-running the
build.

On Windows without Git Bash, `certutil -hashfile spec\openapi.raw.json SHA256` is the sha256 command
and produces the same value.

If `wc -c` agrees and `sha256sum` disagrees, the working copy was converted to CRLF on checkout.
Check that `.gitattributes` still carries the `spec/openapi.raw.json -text` line.

## Pre-process the specification

One command, from the repository root. It takes no arguments.

```
python3 generator/preprocess_spec.py
```

```
python generator/preprocess_spec.py
```

It reads `spec/openapi.raw.json` and writes `spec/openapi.generated.json`, the document the
generator is run against. It then writes the sha256 of that file into `spec/PROVENANCE.json` as
`generatedSpecSha256`. Both outputs are committed.

The patched document is committed rather than built into an ignored path because the diff between
the two spec files is the review artifact of a spec refresh. It shows a reviewer what pre-processing
did to the new pin. A hash recorded over a file no reviewer can open records nothing.

Five transformations run, in this order.

1. T1 narrows root security to the header scheme, so the generated client does not send the key in
   the URL of every request.
2. T2 deletes the malformed root path, which declares a required path parameter that the path
   template carries no placeholder for.
3. T5 declares the success status code each write really answers and attaches the response schema
   each bodiless read really returns. It is described in the next section.
4. T3 derives an operation identifier for every operation from the document itself and assigns it,
   refusing on a name carried by two operations and on a name that is not a valid identifier.
5. T4 rewrites the five schemas shaped like framework types to strings and deletes the five.

The run prints one line per transformation naming what it changed, then a census line, then the byte
count and sha256 it wrote. Compare those lines against the output of a run rather than against a
number written here.

The census is the check, and it is derived rather than compared against a literal. The operations
are counted before any transformation runs, and the number T3 annotated must equal that input count
less the operations T2 removed with the root path. Whisparr adds and removes operations between
releases, so no particular total is asserted; what has to hold is that T2 removed exactly the root
path and nothing else. The census runs after the refusal gate, never beside it, because if T2
refused and the census ran anyway it would pass.

The two spec files differ by cosmetic lines as well as by the five transformations. Python spells an
empty collection `{}` where the .NET writer that produced the captured document spells it `{ }`, and
the patched file ends with a newline where the captured one does not.

Each transformation refuses when it finds nothing to change. An upstream fix therefore fails this
step rather than leaving a rewrite in the pipeline that no longer does anything. The repair is to
delete the transformation, not to weaken it until it passes.

The script is not re-runnable over its own output. Pointing `--raw-spec` at
`spec/openapi.generated.json` makes every transformation refuse at once. That is the correct result
and not a defect.

Run it when a pin moves, after the build and after the sweep, and before generation. Not per change.

`spec/openapi.generated.json` is generated by the script and is never hand-edited.

## The transformation whose input is a measurement

T5 is the third of the five and the only one whose input is not the document. It reads
`spec/CONFORMANCE.json`, which is what `generator/conformance.py` measured against a running
instance.

What it patches is two kinds of thing. Where the record measured a write answering a status other
than 200, it replaces the declared 200 with the code the instance answered, keeping the response at
the position 200 held so the diff stays one line per operation. Where the record names a schema for
an operation that returned data while declaring none, it attaches that schema as the operation's 200
content, wrapped in an array if the record measured an array.

What it does not patch is everything the document already says. An operation the record measured 200
for already declares what it answers, so it belongs to neither kind. A bodiless operation the record
names no schema for returned an object no schema in the document describes, so there is nothing to
attach and nothing is attached.

Both kinds exist only as a measurement. Both are absent `[ProducesResponseType]` annotations
upstream, so building the document from Whisparr's own source supplies neither. Nothing measured is
restated in the transformation: every status code, operation key and schema name comes out of the
record.

It runs at position three, ahead of the operation-identifier derivation, and the position is
load-bearing for exactly three method names. The derivation turns a `Get` prefix into a `List`
prefix when the 200 response declares a JSON array, and it can only see an array response that is
already attached. Every other array-returning read in this SDK is already named for a list, so the
earlier position produces the name the derivation would have given a document that told the truth
about what it returns.

It has four refusals. It refuses when the record was measured against an image other than the one
`spec/PROVENANCE.json` records, so a measurement and a client cannot describe different
applications. It refuses when an operation the record names is absent from the document, or is
present without the response the change replaces, which is the signal that Whisparr moved a path.
It refuses when the record names a schema the document does not declare, because attaching it would
reference nothing. And it refuses when every change it would make has already been made, which is
its zero-condition. That last one is composite over both kinds rather than one per kind: a per-kind
condition would refuse the whole correct document the day upstream annotates one of the two.

The sweep and this transformation are a loop, and the sweep is what keeps it from eating its own
input. An operation the sweep's schema map names is recorded as bodiless whatever the document
declares for it. The document declares a response for it only because this record says what it
returns, so a sweep that re-derived the classification from that declaration would remove the entry,
leave the transformation with nothing to attach, and put the `Get`-prefixed method name back on the
next regeneration.

## Generate the client

One command, from the repository root. It takes no arguments. It requires Docker.

```
python3 generator/generate.py
```

```
python generator/generate.py
```

It runs the pinned generator image
`openapitools/openapi-generator-cli@sha256:2ab0a9680222de65dc9d3baf861aa02b99e1b80c211d8221ebf3ae8f8a102524`,
which is openapi-generator-cli 7.25.0. The digest is held as `DEFAULT_IMAGE_DIGEST` in
`generator/generate.py` and restated in the header of `generator/gen-config.yaml`. The digest is the
pin and the tag is not, because a tag can be moved onto other bytes.

Generation never bind-mounts this repository. It copies `spec/openapi.generated.json` and
`generator/gen-config.yaml` into a fresh temporary root, mounts that, and stages nothing else. There
are two reasons. The generator writes into the root it is given and never prunes, so a run against
the repository in place would mix its output into the working tree before any check had seen it. And
a repository on a mapped or network drive may not be bind-mountable at all: a bind mount of a
mapped-drive path into this image lists as an empty directory and exits 0, while a write into that
mount succeeds inside the container and never reaches the host. That is silent data loss rather than
an error, and it is why there is no output-root parameter.

On Windows the script grants itself an inheritable ACL on the staging root before it mounts it.
Entries the container creates inside the mount inherit that root's ACL, and without the grant the
host cannot read back what the container wrote. `generator/build_spec.py` carries the same grant on
its own scratch root, for the same reason.

If you reproduce the `docker run` by hand in Git Bash, prefix it with `MSYS_NO_PATHCONV=1`. Without
it MSYS rewrites `/local` into a Windows path and the mount target is wrong. Python's `subprocess`
does not go through MSYS, so the script itself is unaffected.

The staged tree is gated before anything committed is deleted. In order:

1. The five generated subdirectories `Api`, `Client`, `Extensions`, `Logging` and `Model` all exist.
2. The three metadata files `.openapi-generator/FILES`, `.openapi-generator/VERSION` and
   `.openapi-generator-ignore` all exist.
3. Every `Model/` and `Api/` file name the spec implies was generated, and no name it does not
   imply.
4. Every method name the spec declares is implemented.
5. `Client/`, `Extensions/` and `Logging/` each hold at least one `.cs` file.
6. The committed tree still matches `generatedTreeSha256`.

Every one of the six runs before the first delete. Step 6 is the pre-flight: it runs after the gate
has approved the staged tree and immediately before the first unlink.

Step 6 refuses on three states, not one. A committed tree whose bytes no longer match the recorded
digest is a hand edit. A committed tree missing one of the five subdirectories is a tree already
damaged, and it refuses rather than treating the absence as a first run. Only a tree with no
recorded digest and none of the five subdirectories is a first run, and that establishes the digest.

Every count the run prints is measured rather than asserted against a literal. It prints how many
`.cs` files it staged, that every method name the spec declares is implemented, how many it copied
back, and the digest it wrote. The method figure is one name per operation, taken from the distinct
generated async method stems with the `OrDefault` twins excluded. A reader who greps the tree for
the async declaration pattern gets twice that, because each operation is emitted with an
`OrDefault` twin, and will otherwise think the run is wrong.

It writes the five subdirectories under `src/Whisparr2.Net/`, `.openapi-generator/`,
`.openapi-generator-ignore` and the one provenance field `generatedTreeSha256`. All of it is
committed, for the same reason the patched specification is: the diff is the review artifact of a
refresh.

```
python3 generator/generate.py --check
```

```
python generator/generate.py --check
```

`--check` runs the identical generation and the identical gate, compares the result against the
committed tree and writes nothing anywhere. A clean check reports that every member of the tree
matches byte for byte. It exits 0 when the committed tree is byte-identical to a fresh generation, 1
when it differs or the gate refused, and the generator's own exit code when the image itself failed.

Nothing under `src/Whisparr2.Net/` except `Whisparr2.Net.csproj` is ever hand-edited. The csproj is
hand-owned and sits beside the five generated subdirectories, which is why the delete iterates the
five and never the package root. When the method census refuses because the generator renamed an
operation, the repair is an override entry in `generator/preprocess_spec.py`, never an edit under
the generated tree. A hand edit there is discarded by the next run, and refused by the pre-flight
before that.

On Windows a regeneration can fail partway through the copy with a sharing violation, because
MSBuild node processes hold build directories open. Run `dotnet build-server shutdown` first, then
re-run the generator.

Run it when a pin moves, after pre-processing. Not per change.

## Why the pinned image is taken to be Whisparr 2

No script asserts it. The Whisparr `v2` branch and the `v2` image line are taken to correspond, and
the evidence is that the pinned commit was committed six minutes before the image's own reported
build time. That is corroboration rather than proof, and it is recorded here so a reader is not
looking for a check that does not exist.

An identity assertion would not add much even if it were carried. The same image name serves tags
for Whisparr 3, and the application name and the API prefix are identical on both, so neither of
those discriminates. Branch and major version do discriminate between the two lines, and they say
nothing at all about which instance answered, because a personal Whisparr 2 library running the
same release reports exactly the same values.

What protects a live run is two things, and neither is a claim about a version. The address is
constructed in one place: `generator/container.py` publishes an ephemeral port on the loopback
interface and reads it back from the container it created, and nothing anywhere names a host port.
And `generator/conformance.py` refuses an instance whose reported start time predates the moment
this run began its boot, which is the one signal a long-running instance on the pinned image cannot
satisfy. The integration suite carries the same address rule, enforced by a gate over its own
source.

## Record what a running instance returns

One command. It requires Docker.

```
python3 generator/conformance.py
```

```
python generator/conformance.py
```

It boots the pinned digest under a name unique to the run, waits for the log line the application
writes once its startup handlers have returned, calls every read it can address without inventing
state, issues every write it can make a fresh instance answer, and writes `spec/CONFORMANCE.json`
and nothing else. The container is removed whether the run succeeded or failed, so nothing is left
holding a published port and a live key.

The sweep records and it does not judge. It used to compare each response against the schema the
document declared for it, and refuse on an undeclared property, a wrong JSON type, an explicit null
or an out-of-set enum value. All four became impossible when the document started being built from
the commit the pinned image runs: a document and an application built from one commit cannot
disagree about a declared property or a declared type. The four verdicts, the recursive comparison
that produced them and their refusals are gone, and the run exits 0.

What is left is the measurement, and it is what the fifth pre-processing transformation reads. The
file records how many reads were selected and how many were recorded against a declared schema, the
success status each write answered, every write the probe could not make a fresh instance answer
with the status it did answer and the reason, every operation that returned data while declaring
none with its content type, byte count and top-level shape, the non-JSON reads, and the reads that
did not answer 200.

The reads are three tiers, derived from the document rather than written down. Tier 1 is every GET
that carries no path parameter. Tier 2 is a by-id GET whose id a tier 1 collection read can supply,
and a by-id read whose collection returned no row is left uncalled rather than fed a value from
source. Tier 3 is every other parameterised GET, which needs a row or a real filename, and the
sweep does not call it. The run prints how many reads it selected and how many of the document's
GETs it recorded against a declared schema.

The writes are a probe rather than a sweep. It creates rows it can create, issues the bulk update
and bulk delete each provider carries, reorders a delay profile, and removes what it created. Every
row it creates is disabled, so it answers the writes exactly as an enabled one would and reaches no
network on the way. A write the probe could not make a fresh instance answer with success is
recorded under a separate key, beside the status it did observe and the reason, and never as a
success code.

`declaredNeverReturned` sits in the same file and is not a patch list. It is the properties a
touched schema declares that no body on a fresh instance carried, which is a fact about an empty
instance rather than about the document. `DownloadClientResource.id` is returned the moment a
download client exists, and `Field.helpTextWarning` is returned by any provider field that carries a
warning, so treating the list as a patch list would delete both from the generated models. It is
also not reproducible across two boots of the same digest: one boot carried two `LogResource`
properties because a log row held an exception, and another carried `HealthResource.id` because that
boot raised a health issue. The offline and Docker self-tests assert it is non-empty and compare no
entry.

`spec/CONFORMANCE.json` records a JSON type name and never an observed value. `GET
/api/v3/config/host` returns the instance API key in plaintext and its schema declares four more
credentials beside it, so a record that carried values would commit a credential on every run.

One read sits behind `WHISPARR2NET_CONFORMANCE_EXTERNAL`. Set it to `1` and the run also calls the
series lookup, which answers 200 only by reaching a metadata service over the public internet. It is
off by default, and a hermetic run must leave it off. The file records whether the probe ran, so an
empty result from a hermetic run is not read as a run that looked and found nothing. The committed
file came from a flagged run.

Run it when a pin moves, and before generation, because the fifth transformation reads what it
records. Not per change.

## Check the client against a running instance

The integration suite boots the same pinned digest through the same module and drives the generated
client against it. It covers reads whose bodies reach a rewritten schema, a create-read-update-delete
round trip against a real instance, and a read-modify-write round trip that asserts a field the
document does not declare survives the write.

`ExternalLookupTests` sits behind the same `WHISPARR2NET_CONFORMANCE_EXTERNAL` flag the sweep uses,
for the same reason: the operation it calls answers 200 only by reaching outside the container, so
on a machine with no route out an ungated assertion there fails and the failure reads as a
deserialization defect in this client. The array response that operation carries is proved without
Docker and without a network in the unit project, over a loopback listener, and that is what a
per-change check runs.

The suite reports its own state in words rather than in an exit code, and three of its four states
exit 0. A run that produced any result at all prints exactly one summary line per target framework,
opening with `Passed!`, `Skipped!` or `Failed!`. A run that discovered no test prints `No test is
available in <dll>` and no summary line at all, so the absence of a summary line is the signal. A
check written against a summary line reporting a total of zero would never match, because that line
is never printed. Set `WHISPARR2NET_REQUIRE_DOCKER` to `1` to declare that a run must produce live
evidence: such a run fails when no daemon is reachable, rather than reporting a green skip.

## Refresh the whole pipeline

Four commands, in this order. Each one writes a committed artifact.

```
1. python generator/build_spec.py
2. WHISPARR2NET_CONFORMANCE_EXTERNAL=1 python generator/conformance.py
3. python generator/preprocess_spec.py
4. python generator/generate.py
```

In PowerShell, step 2 is `$env:WHISPARR2NET_CONFORMANCE_EXTERNAL=1; python
generator/conformance.py`.

Step 2 carries the flag, and a refresh is the one place it is not optional. The committed
`spec/CONFORMANCE.json` came from a flagged run, and the fifth pre-processing transformation reads
that file. A hermetic sweep records one fewer bodiless operation, so step 3 attaches one fewer
response schema. The name derivation runs after that attachment, so step 3 then derives
`GetSeriesLookup` where the committed client carries `ListSeriesLookup`, and step 4 emits the
renamed method. The flag needs the outbound network route step 1 needs.

Step 2 must precede step 3. The fifth pre-processing transformation reads `spec/CONFORMANCE.json`,
so a refresh that pre-processes before sweeping applies the previous run's measurement to a document
built from the new commit. The transformation refuses when an operation the record names is absent
from the document, so a moved path is caught, but a record that still resolves against the new
document is applied silently and is stale.

Step 3 must precede step 4. `generator/generate.py` stages `spec/openapi.generated.json`, which is
step 3's output, so running step 4 first regenerates the client from the previous pin and reports
nothing wrong.

Step 2 also reads step 1's output, through `spec/openapi.generated.json` and `spec/PROVENANCE.json`,
so it is not independent of the build either. The order above is the only one that works.

Follow the four with `dotnet build Whisparr2.Net.slnx`, which must report 0 errors and 0 warnings on
both target frameworks.

A refresh over an unmoved pin reproduces `spec/openapi.raw.json`, `spec/openapi.generated.json` and
the whole generated tree byte for byte. Two diffs are expected even so, and neither is a finding.

`spec/PROVENANCE.json` moves on its `builtAt` line, which is the wall clock of the build. Its two
hash keys also settle into the order a refresh produces: step 1 removes `generatedSpecSha256` and
step 3 adds it back as a new last key, so it comes to sit after `generatedTreeSha256`.

`spec/CONFORMANCE.json` can move by an entry or two under `declaredNeverReturned`, which is the one
key in it that is not reproducible across two boots of the same digest. A boot that raises a health
issue or writes a log exception carries properties an idle boot does not. Read the diff, and commit
it or discard it on its merits: the rest of the record is compared entry for entry by
`python generator/selftest.py --docker`.

There is no single command that runs all four. Each writes a committed artifact and each has its own
refusals, and a wrapper that hides which of them refused is worse than four lines a reader can run
one at a time.

## Checking the scripts themselves

`python generator/selftest.py` runs 27 offline assertions over the build, the pin, the five
pre-processing transformations, the generation gate, the integration suite's addressing and the
conformance sweep's refusal branches. It needs no network and no Docker.

`python generator/selftest.py --docker` adds two more, for 28: a full regeneration compared against
the committed tree, and a hermetic sweep of a live instance compared against the committed record.
Both need the pinned image and together they take a few minutes.

There is no group that reaches the network. The only subject a network check ever had was a
read-only proposal against real upstream commits, and the document is built here now rather than
read out of another repository. A flag over an empty group would report success without having run
anything, so no such flag exists.

Every one of them is run by hand today.
